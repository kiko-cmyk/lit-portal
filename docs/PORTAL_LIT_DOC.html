P. 02

01 · Resumen ejecutivo

Qué es el portal, qué consigue el cliente, qué consigue LIT.
PORTAL LIT
Sección 01

El Portal de Cliente de LIT es la nueva área privada donde el suscriptor gestiona su caja: cambia el plan, salta envíos, modifica la dirección, añade extras, y, llegado el caso, cancela. Sustituye al portal genérico que venía por defecto con la herramienta de suscripciones (Seal), que vivía en un dominio distinto y rompía la identidad de marca.

El porqué

El portal antiguo era una página técnica, fea, en otro dominio (tracking.litsalt.com). Tener uno propio significa que el cliente jamás sale de litsalt.com, ve la identidad LIT en todo momento, y nosotros controlamos cada flujo (cancelación, win-back, recompensas) en lugar de depender de lo que Seal ofrezca por defecto.

Lo que consigue el cliente
Self-service
Total
Saltar caja, cambiar plan, dirección y pago en un click.
Sin salir de marca
litsalt
Todo el flujo dentro de /apps/portal/*.
Cancelación
4 pasos
Con alternativas antes del fin: skip, plan, sabor.
Visibilidad
100%
Próximas entregas, historial, sabor, dirección.
Lo que consigue LIT
  • Reducción de tickets a soporte — la mayoría de "skip mi caja" / "cambiar plan" pasan a self-service.
  • Marca consistente de extremo a extremo. Misma tipografía, mismo idioma, mismo trato.
  • Recuperación de cancelaciones integrada en el propio flujo: el cliente ve alternativas antes de la decisión final.
  • Telemetría limpia: cada acción se loguea en Klaviyo (skip, cancel reason, plan change) para alimentar flujos automáticos de retención.
  • Control sobre el roadmap: Drops, Collection, Inner Circle, eventos en Madrid/Barcelona — fases siguientes ya con el chasis montado.
Estado actual

El portal está desplegado en producción en litsalt.com/apps/portal/*. Los flujos críticos (login OAuth, ver suscripción, saltar, cambiar plan, cambiar dirección, cancelar) funcionan end-to-end. Hay una auditoría de seguridad ejecutada el 21 de mayo de 2026 con findings documentados aparte (docs/SECURITY_AUDIT_2026-05-21.md). Las fases siguientes — Collection (cartas), Drops (recompensas), Inner Circle (tier reward) — tienen el schema listo en Supabase y la UI con stubs.

Las piezas, una por una
Next.js 16
App Router. Server components para precargar datos sin exponer tokens al bundle del cliente. SSR para first paint rápido.
Shopify App Proxy
El cliente nunca sale de litsalt.com. Shopify firma cada request con HMAC y nos adjunta el customer_id.

Convenciones
  • Idiomas: bilingüe ES/EN vía componente <T en="..." es="..." />. URL incluye locale (/es/mi-lit, /en/mi-lit).
  • Mutations: todas pasan por withCustomer middleware que verifica auth (App Proxy HMAC o Bearer/X-LIT-Session) antes de procesar.
  • Fast-path: el cliente manda sealSubscriptionId en el body de mutations para que el backend evite el scan paginado de 33 páginas de Seal (~5s vs ~300ms).
  • Cutoff: ventana de 24h antes del próximo envío durante la cual no se permiten cambios (skip, plan, dirección, extras). Constante única en src/lib/cutoff.ts.
  • Sin guiones largos (em-dash) en NINGÚN copy. Decisión de marca. Usar coma o punto.
Decisión de marca

Toda la UI del portal usa las tipografías brand (Barlow y Barlow Condensed) y los colores LIT (cream #F8F9F2, lit-grey #323743, bold-yellow #EBEE62). No hay hojas de estilo "neutras" — todo es brand consistente.

03 · Autenticación y sesiones

Dos mecanismos de auth coexistiendo. Cualquiera identifica al cliente.
PORTAL LIT
Sección 03

El middleware withCustomer intenta dos vías de identificar al cliente. La primera funciona cuando el cliente entra desde el storefront de Shopify (típicamente desde un email). La segunda cuando el cliente entra directamente.

Vía A · Pasiva
App Proxy
Shopify firma la URL con HMAC y adjunta logged_in_customer_id. Transparente: si está logueado en la storefront, ya está dentro.
Vía B · Activa
OAuth (PKCE)
Customer Account API. Tras el callback creamos un session_id opaco en Supabase. El FE lo manda en X-LIT-Session.
Diagrama del flujo OAuth (Vía B)
Cliente Portal (Vercel) Shopify │ │ │ │ GET /apps/portal/. │ │ ├──────────────────────►│ │ │ │ no proxy auth, no token │ │ │ redirect /login │ │◄──────────────────────┤ │ │ → /authorize (PKCE, code_verifier, │ state = signed JWT) ├────────────────────────────────────────────────►│ │ │ │ login + consent │ │◄───────────────────────────────────────────────┤ │ │ ?code=... &state=... ├──────────►/api/auth/callback ──────────────────►│ │ │ exchange code → tokens │ │ │◄────────────────────────┤ │ │ │ │ INSERT row auth_sessions │ │ con session_id opaco │ │ redirect /handoff?s= │ │◄──────────────────────┤ │ (handoff page mueve session_id │ a localStorage → 'lit_session') │ │ Autenticado mediante X-LIT-Session header │ desde aquí en adelante
Por qué X-LIT-Session y no Authorization: Bearer
GotchaShopify intercepta Authorization en mutations
Shopify App Proxy intercepta el header Authorization en peticiones POST/PATCH/DELETE y NO las reenvía al upstream. En su lugar devuelve un 500 con el HTML del tema (la home de la tienda), lo cual hace que el FE crea que el endpoint está roto. Headers custom X-* pasan limpios. Migramos a X-LIT-Session y todas las mutations volvieron a funcionar al instante.

Logout, sesiones en Supabase, y guardas server-side.
PORTAL LIT
Sección 03 · cont.
Tabla auth_sessions (Supabase)
ColumnaTipoPropósito

customer_idtextShopify customer_id (numeric, p.ej. 27453541548381).
emailtextEmail del cliente (cacheado del id_token).

Logout

El endpoint /api/auth/logout:

  1. Borra la fila de auth_sessions en Supabase.
  2. Construye la URL de logout OIDC de Shopify con id_token_hint + post_logout_redirect_uri.
  3. El FE limpia su localStorage (clearSessionToken) y hace window.location.replace a esa URL.
  4. Shopify invalida la sesión storefront y redirige al cliente al destino configurado.
Caso especial

Tras una cancelación, el botón "Volver a LIT" del done state ejecuta el flujo de logout completo y manda al cliente a litsalt.com (homepage). No quiero que el cliente vuelva al portal y vea estado stale (sub "todavía activa" en la UI local mientras Seal ya la canceló). Salir limpio.

Sub-guard: protección contra IDOR

El helper assertSubscriptionBelongsToCustomer (src/lib/sub-guard.ts) se ejecuta antes de CADA mutation sobre una sub. Compara el sub.email de Seal contra el email del Shopify customer autenticado. Si no matchean → 403 inmediato y log de auditoría con ambos emails. Se añadió tras un near-incident en el que Seal devolvió la sub de otro cliente en una pagination edge case.

04 · Superficies del portal

Skip, Plan, Address, Payment, Extras — las mutations.
PORTAL LIT
Sección 04 · 2/3
4.3 · Skip overlay
POST /api/subscription/skip
OVERLAYMUTATION
Bottom-sheet en móvil, modal centrado en desktop. Muestra "¿Te vas de viaje?", la fecha de envío actual, y un botón "Confirmar saltar". Al confirmar:
  • POST con sealSubscriptionId en el body (fast-path).
  • Backend valida ownership en Supabase, hace GET dirigido a Seal por ID (sin paginar), comprueba cutoff de 24h, llama skipBillingAttempt.
  • FE recibe la nueva fecha, marca justSkipped en localStorage con expiry hasta esa fecha, dispara evento Klaviyo.
4.4 · Plan overlay
PATCH /api/subscription/plan
OVERLAYMUTATION
Selector de cajas (1 a 6) + selector de frecuencia (15d hasta 6 meses). Precio dinámico desde Shopify con compareAtPrice tachado si aplica descuento. Si hay skip activo, banner amarillo: "Al cambiar el plan, tu salto de caja se deshará". Al guardar:
  • Si cambia frecuencia: seal.editSubscription(delivery_interval) primero.
  • Si cambia nº de cajas: addItems con nueva variant, luego removeItems de la antigua. Seal no permite swap directo.
  • Pausas de 500ms entre mutations porque Seal regenera billing_attempts en background.
  • Verify post-mutation con AbortController de 4s. Si timed out → respuesta sintética + FE arranca re-poll silencioso de 60s.
4.5 · Address overlay
PATCH /api/subscription/address
OVERLAYMUTATION
Formulario para cambiar dirección de envío. PATCH llama a seal.updateShippingAddress. Aplica cutoff de 24h.
4.6 · Payment method
Shopify customerPaymentMethodSendUpdateEmail
EMAIL-ONLY
Decisión locked 2026-05-19: 100% email-only. El botón "Cambiar método de pago" dispara Shopify Admin API, que envía un enlace seguro al email del cliente. El portal muestra: "Te hemos enviado un enlace a tu correo, vuelve aquí al terminar". Sin Stripe, sin pasarela nueva.

El takeover de cancelación: el flujo más cuidado del portal.
PORTAL LIT
Sección 04 · 3/3
4.7 · Cancel takeover
/api/subscription/cancel (steps 1 → 4)
FULL-SCREEN WIN-BACK MULTI-STEP
No es un overlay, es un takeover oscuro a pantalla completa que ocupa toda la viewport. 4 pasos:
Step 01
Stats
"Has recibido N cajas y llevas M meses en LIT". Reconocer el viaje del cliente antes de proponer salirse.
Step 02
Alternativas
Botones para Saltar, Cambiar plan o Sabores. Pivotan al overlay correspondiente SIN cerrar el takeover.
Step 03
Motivo
Selector de razón (caro / mucho producto / no lo uso / pausa / otro) + free text opcional.
Step 04
Confirmación
Copy condicional según cutoff. Botón final "Cancelar suscripción".
Qué pasa al confirmar
  1. Marca la cancellation row en Supabase como committing (estado intermedio para detectar cancels colgados).
  2. Llama seal.cancelSubscription (es inmediato — Seal pone cancelled_on al momento).
  3. Promueve la row a confirmed con timestamp.
  4. Si es second-cancel: reset inmediato del balance Drops. Si es first: hold de 90 días.
  5. Dispara evento Klaviyo subscription_cancelled con razón, freeText, cancelCount, fecha último envío, drops hold.
  6. Muestra el done state: "Muchas gracias por haber confiado en LIT. Ojalá poder tenerte de vuelta pronto."
Salida limpia

El botón "Volver a LIT" del done state hace logout completo (borra session en Supabase, limpia localStorage) y redirige a litsalt.com. El cliente NO vuelve al portal con estado stale. Si más tarde quiere volver a entrar, el Hub le mostrará el ReactivateCard.

4.8 · Login / EmptyState
/apps/portal/[es|en]/mi-lit (sin auth)
FALLBACK
Sin sesión → LoginScreen con CTA a OAuth. Autenticado pero sin suscripción activa (one-shot buyer o cancelado) → EmptyState con "Gracias por probar LIT" + CTA a la página de suscripción con descuento "desde el 25%".

06 · Decisiones y aprendizajes

Los gotchas que aprendimos por las malas. Para que no se repitan.
PORTAL LIT
Sección 06 · 1/2
GOTCHA 01Shopify App Proxy sustituye 5xx con HTML del storefront
Cuando el upstream (Vercel) devuelve un HTTP 5xx, App Proxy NO reenvía esa respuesta al cliente. En su lugar, renderiza el HTML del tema de la tienda con la URL solicitada como canonical. El cliente recibe ~50KB de markup del storefront con status 500, pero content-type: text/html y headers de Shopify (powered-by: Shopify, server-timing: theme;desc=...).
Diagnóstico: bypass del proxy y hablar directo con Vercel (curl https://lit-portal-drab.vercel.app/...) para ver el error JSON real. Nos costó horas descubrir esto.
GOTCHA 02Seal regenera billing_attempts en cada plan change
Cualquier editSubscription en Seal (cajas, frecuencia, dirección, items) hace que regenere la lista de billing_attempts desde cero. Cualquier skip aplicado previamente se borra silenciosamente.
Mitigación: el FE limpia el flag justSkipped de localStorage cuando hay plan change exitoso, y el PlanOverlay avisa con banner amarillo si hay skip activo antes de cambiar plan.
GOTCHA 03Eventual consistency en Seal
Tras una mutation, un GET inmediato puede devolver datos stale (un attempt aparece como pendiente cuando ya está marcado skipped).
Soluciones: (1) el skip endpoint computa el nuevo nextShipDate localmente en vez de re-fetch; (2) el plan endpoint usa AbortController con timeout de 4s; (3) el FE arranca re-poll silencioso de 60s tras un plan change.
GOTCHA 04Constraint check sin migration aplicada en prod
El código del cancel step 4 escribía status='committing' antes de llamar a Seal, pero la constraint CHECK del schema solo permitía ('pending','confirmed'). Durante semanas nadie podía cancelar — el portal devolvía 500 que Shopify convertía en HTML del storefront (Gotcha 01 enmascarando esto).
Fix: ALTER CONSTRAINT aplicado el 2026-05-21. Migration en database/migrations/. Schema canónico sincronizado.
GOTCHA 05Cancel es INMEDIATO en Seal (no después del último envío)
El comportamiento por defecto de Seal cancel pone cancelled_on al instante, no tras el último envío. El portal refleja esto en el copy de confirmación según el cutoff: "Cancelación inmediata", excepto si el próximo envío ya está procesando dentro de 24h, en cuyo caso ese último sí sale.

06 · Decisiones y aprendizajes

Las reglas duras de marca y producto.
PORTAL LIT
Sección 06 · 2/2
REGLA 06El cliente JAMÁS ve tracking.litsalt.com
Regla dura: el cliente final no puede ver, en ningún momento, el portal de tracking antiguo. Todo el flujo de su cuenta vive dentro de litsalt.com/apps/portal/*. Cambio de método de pago = email. Cancel = takeover. Error = inline. El portal viejo "dejará de existir" para el cliente final.
REGLA 07Sin em-dashes (—) en NINGÚN copy
Hard rule de marca: ningún copy de LIT (portal + emails + ads) puede llevar un em-dash. Usar coma o punto. Preferencia consistente del founder. Lint cuando se genera contenido nuevo.
REGLA 08Cutoff bajado de 72h a 24h
Decidido el 2026-05-21: el operador interno necesita al menos 24h para procesar cambios antes del envío. Antes eran 72h, que bloqueaba demasiados cambios que sí se podían atender. Se aplica a skip, plan, address, extras. Constante única en src/lib/cutoff.ts.
REGLA 09Cambio de método de pago = email-only
Decisión locked 2026-05-19: el cambio de método de pago es 100% email-only via Shopify customerPaymentMethodSendUpdateEmail. Sin Stripe, sin pasarela nueva. Shopify ya tiene el método de pago y la pasarela — el portal solo dispara el envío del enlace seguro.
REGLA 10Auth segura por defecto: X-LIT-Session no Authorization
Tras el descubrimiento del 2026-05-21 (Shopify App Proxy bloquea Authorization en mutations), el portal envía el session token en header custom X-LIT-Session. El backend acepta ambos para back-compat, pero el FE solo usa el custom. Esto resolvió de raíz una clase entera de bugs ("la mutation parece que funciona pero nunca llega al servidor").
Cierre

El portal está vivo, los flujos críticos funcionan end-to-end, y el cliente puede gestionar su suscripción sin ver el portal antiguo. La base es sólida. Las decisiones documentadas en estas dos páginas son las que evitarán que el equipo repita los mismos errores cuando llegue Fase 2 (Collection, Drops, Inner Circle) o cuando se monte un nuevo portal para otra marca con la misma arquitectura.
